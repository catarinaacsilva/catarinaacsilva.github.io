\begin{frame}
\frametitle{Porque Precisamos de Gestão Centralizada}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item Uma infraestrutura de cloud reúne centenas ou milhares de componentes, como servidores, switches, routers e storage.
    \item Verificar manualmente o estado de cada equipamento não escala.
    \item É preciso um protocolo comum, independente do fabricante, para consultar e alterar o estado de qualquer dispositivo gerido.
    \item O SNMP (Simple Network Management Protocol) surgiu nos anos 1980 com este objetivo.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{Arquitetura SNMP \textcolor{NudeTaupe}{\small(1/2)}}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item O manager é a estação de gestão, que consulta os dispositivos e recebe as suas notificações.
    \item O agente é o software que corre no dispositivo gerido (servidor, switch, impressora) e responde ao manager.
    \item A comunicação usa tipicamente UDP, a porta 161 para os pedidos e a 162 para as traps, para reduzir o overhead de gestão.
    \item Um manager pode gerir centenas de agentes distribuídos pela infraestrutura.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{Arquitetura SNMP \textcolor{NudeTaupe}{\small(2/2)}}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item A MIB (Management Information Base) é a estrutura hierárquica que descreve as variáveis geríveis de um dispositivo.
    \item O OID (Object Identifier) é o identificador numérico único de cada variável, por exemplo \texttt{1.3.6.1.2.1.1.3.0} para o uptime do sistema.
    \item A MIB é uma árvore, em que cada ramo pertence a uma organização ou fabricante, e a IANA atribui os ramos de topo.
    \item Sem OIDs normalizados, cada fabricante exporia a mesma informação à sua maneira.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{A Árvore MIB e a MIB-II}
\begin{itemize}
    \setlength\itemsep{0.35cm}
    \item A MIB é uma árvore hierárquica. Cada nó tem um número, e o caminho da raiz à folha forma o OID.
    \item O ramo mais usado é \texttt{1.3.6.1}, que corresponde a \texttt{iso.org.dod.internet}.
    \item O ramo \texttt{1.3.6.1.2.1} é a MIB-II, o conjunto normalizado de objetos que praticamente todos os dispositivos implementam.
    \item Entre os seus grupos estão o \texttt{system} (\texttt{1.3.6.1.2.1.1}), o \texttt{interfaces} (\texttt{1.3.6.1.2.1.2}) e o \texttt{ip} (\texttt{1.3.6.1.2.1.4}).
    \item O ramo \texttt{1.3.6.1.4.1} é o enterprises, onde cada fabricante recebe da IANA um número próprio para as suas extensões.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{SMI, Tipos de Dados e Ficheiros MIB}
\begin{itemize}
    \setlength\itemsep{0.15cm}
    \item A SMI (Structure of Management Information) define as regras de escrita das definições da MIB.
    \item Os tipos comuns incluem \texttt{INTEGER}, \texttt{OCTET STRING}, \texttt{Counter32}, \texttt{Gauge32} e \texttt{TimeTicks}, este em centésimos de segundo.
    \item O \texttt{Counter32} só cresce e volta a zero ao transbordar, e o \texttt{Gauge32} sobe e desce.
    \item Num contador interessa a variação entre leituras e não o valor absoluto. Em interfaces rápidas usam-se contadores de 64 bits.
    \item Um ficheiro MIB é um documento de texto que descreve estes objetos e permite traduzir OIDs numéricos em nomes legíveis.
    \item Sem o ficheiro MIB, as ferramentas mostram apenas números, o que é funcional mas difícil de interpretar.
\end{itemize}
\end{frame}

\figframe{Counter e Gauge}{a12-counter-gauge}

\begin{frame}
\frametitle{Evolução das Versões \textcolor{NudeTaupe}{\small(1/2)}}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item O SNMPv1 é a versão original, simples e sem mecanismos de segurança reais.
    \item O SNMPv2c melhora o desempenho, por exemplo com o GETBULK, mas mantém a autenticação por community string.
    \item A community string funciona como uma palavra-passe, mas é transmitida em texto simples na rede.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{Evolução das Versões \textcolor{NudeTaupe}{\small(2/2)}}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item O SNMPv3 introduz autenticação real e cifra do tráfego de gestão.
    \item Corrige a principal fragilidade das versões anteriores, que expunham credenciais e dados de gestão em texto simples.
    \item O SNMPv2c continua muito usado em ambientes legados, pela simplicidade de configuração.
    \item Em produção, o SNMPv3 é a escolha recomendada sempre que a segurança da rede de gestão conta.
\end{itemize}
\end{frame}

\figframe{Versões do SNMP}{a12-versoes}

\begin{frame}
\frametitle{SNMPv3 e o Modelo de Segurança USM}
\begin{itemize}
    \setlength\itemsep{0.35cm}
    \item O USM (User-based Security Model) substitui a community string por utilizadores com credenciais próprias.
    \item Há três níveis de segurança, \texttt{noAuthNoPriv} sem autenticação nem cifra, \texttt{authNoPriv} só com autenticação e \texttt{authPriv} com autenticação e cifra.
    \item A autenticação usa HMAC, tipicamente com SHA, e a cifra usa tipicamente AES.
    \item Garante também integridade, porque a mensagem não foi alterada em trânsito, e proteção contra a repetição de mensagens antigas.
    \item O VACM (View-based Access Control Model) define que ramos da MIB cada utilizador pode ler ou escrever.
\end{itemize}
\end{frame}

\figframe{Níveis de Segurança do SNMPv3}{a12-usm-niveis}

\begin{frame}
\frametitle{Operações do Protocolo \textcolor{NudeTaupe}{\small(1/2)}}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item O GET pede ao agente o valor de um OID específico.
    \item O GETNEXT pede o OID seguinte na árvore da MIB, o que permite percorrer tabelas sem conhecer todos os OIDs.
    \item O GETBULK, do SNMPv2c e v3, pede vários valores de uma vez e reduz o número de mensagens.
    \item O SET altera o valor de uma variável no agente, por exemplo para reconfigurar um parâmetro remotamente.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{Operações do Protocolo \textcolor{NudeTaupe}{\small(2/2)}}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item O GET e o SET são síncronos, porque o manager pergunta e o agente responde.
    \item A TRAP é um mecanismo assíncrono em que o agente notifica o manager sem pedido prévio, por exemplo quando uma interface cai.
    \item O INFORM é como a TRAP, mas com confirmação de receção pelo manager, o que a torna mais fiável.
    \item O modelo pull (GET) mais push (TRAP e INFORM) cobre consultas periódicas e eventos urgentes.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{Net-SNMP, Ferramentas de Referência}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item O net-snmp é a implementação open source de referência do SNMP.
    \item O \texttt{snmpd} corre no dispositivo gerido e faz o papel de agente.
    \item O \texttt{snmpget} e o \texttt{snmpwalk} são utilitários de linha de comandos que consultam OIDs individuais ou percorrem ramos inteiros da MIB.
    \item O \texttt{snmptrapd} recebe as traps enviadas pelos agentes.
    \item Está disponível na generalidade das distribuições Linux, o que o torna uma boa base para aprender e testar.
\end{itemize}
\end{frame}

\figframe{Ferramentas do Net-SNMP}{a12-net-snmp}

\begin{frame}
\frametitle{Polling e Push, e o que Medir}
\begin{itemize}
    \setlength\itemsep{0.3cm}
    \item No polling, o manager consulta periodicamente cada agente com GET. É simples, mas o intervalo determina a rapidez de deteção.
    \item No push, o agente notifica quando algo acontece, com TRAP ou INFORM. A deteção é imediata, mas exige que o agente esteja funcional.
    \item Um intervalo de polling curto deteta mais depressa, mas gera mais carga sobre a rede e os dispositivos.
    \item As métricas habituais são CPU, memória, espaço em disco, tráfego e erros por interface, temperatura e estado das fontes de alimentação.
    \item Convém recolher também a ausência de resposta, porque um agente que deixa de responder é, em si, um sinal relevante.
\end{itemize}
\end{frame}

\figframe{Polling e Push no Tempo}{a12-polling-push}

\begin{frame}
\frametitle{Alarmística e Fadiga de Alertas}
\begin{itemize}
    \setlength\itemsep{0.3cm}
    \item Recolher métricas só é útil se houver critérios claros que transformem valores em ação.
    \item Os limiares (thresholds) definem a partir de que valor uma métrica gera alerta.
    \item A histerese usa limiares diferentes para disparar e para repor o alerta, e evita a oscilação constante junto ao limite.
    \item A fadiga de alertas surge quando há alertas a mais e os operadores deixam de lhes prestar atenção, o que faz passar despercebidos os importantes.
    \item A boa prática é alertar sobre sintomas com impacto no utilizador e deixar as restantes métricas para diagnóstico posterior.
\end{itemize}
\end{frame}

\figframe{Limiares e Histerese}{a12-histerese}

\begin{frame}
\frametitle{O SNMP no Panorama Atual}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item O Nagios e o Zabbix são sistemas de monitorização mais completos que usam frequentemente o SNMP como um dos métodos de recolha.
    \item O Prometheus é um modelo mais recente, baseado em métricas expostas por HTTP e recolhidas por pull.
    \item O SNMP mantém-se relevante sobretudo em equipamento de rede legado, que só expõe gestão por esta via.
    \item Existem pontes, como o snmp\_exporter, que levam dados SNMP para o Prometheus.
    \item As tecnologias coexistem, e cada uma tem o seu nicho consoante o equipamento e a idade da infraestrutura.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{Síntese da Aula \textcolor{NudeTaupe}{\small(1/2)}}
\begin{itemize}
    \setlength\itemsep{0.4cm}
    \item Infraestruturas de cloud com muitos componentes exigem gestão centralizada e normalizada.
    \item O SNMP assenta em managers, agentes, MIB e OIDs para endereçar cada variável gerida.
    \item O SNMPv1 e o v2c são simples mas inseguros, e o v3 acrescenta autenticação e cifra.
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{Síntese da Aula \textcolor{NudeTaupe}{\small(2/2)}}
\begin{itemize}
    \setlength\itemsep{0.35cm}
    \item O GET, GETNEXT, GETBULK e SET são síncronos (polling), e a TRAP e o INFORM notificam eventos de forma assíncrona (push).
    \item O SNMPv3 acrescenta autenticação, cifra e controlo de acesso por vistas, com o USM e o VACM.
    \item O net-snmp (snmpd, snmpget, snmpwalk) é a implementação de referência, e os ficheiros MIB traduzem OIDs em nomes.
    \item Recolher métricas só é útil com limiares bem escolhidos, e alertas a mais levam a fadiga e a incidentes ignorados.
\end{itemize}
\end{frame}
